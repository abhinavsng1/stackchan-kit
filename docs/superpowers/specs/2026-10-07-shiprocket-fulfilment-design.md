# Shiprocket fulfilment and COD collection

**Date:** 2026-10-07
**Status:** approved in conversation, awaiting written review

## What this is for

Pebble Robotics sells one product in two arms. The buyer pays a ₹499 deposit
online through Razorpay; the rest is collected in cash when the courier hands
the parcel over. Today nothing exists between "they paid the deposit" and
"somebody posts a box". This design builds that middle.

Success is three things, in order of how much they matter:

1. A unit that has been built can be dispatched without leaving the admin.
2. The remaining balance reaches the company's bank account, and the system
   knows when it has — not when a courier says the parcel was delivered.
3. The buyer's address goes to exactly one logistics company, and the privacy
   page says so before the first parcel ships.

It is explicitly **not** a warehouse system, a returns system, or a courier
rate-shopping system. One pickup address, one product, one courier choice per
order.

## Decisions already taken

These were settled in conversation and are not open in this document.

**Dispatch is manual, one order at a time.** Orders sit in the admin list; a
human presses Ship. Automatic dispatch on payment was rejected: the build
takes two to three weeks, so a courier booked at payment time is booked for a
robot that does not exist. A human pressing Ship is also the only check that
the address is sane and the unit is actually finished.

**The COD amount is encoded as Option A.**

```jsonc
{ "payment_method": "COD", "sub_total": 4999, "partial_cod_collected": 499 }
```

Shiprocket is told the true order value and how much is already in. The
alternative — sending only the ₹4,500 owed as `sub_total` — was rejected as
less honest about what the order is worth, though it is the unambiguous one.
See "The amount the courier collects" below, which treats this as a risk
rather than a settled fact.

**The admin branch merges first.** `feat/insights-dashboard` carries admin
authentication, the orders page, and the `fulfilment` / `archived_at` columns.
It merges to `main` before this work starts, so the Ship button lands on the
orders page that already exists and reuses one state machine instead of
inventing a parallel one. Verified 2026-10-07: 17 commits, merges clean with
no conflicts.

## The amount the courier collects — the one real risk

Shiprocket's OpenAPI spec documents `partial_cod_collected` as *"Amount
already collected for partial COD; must be >= 0 and less than sub_total."*
That is the entire documentation. **Nothing in Shiprocket's documentation
states what the delivery agent is actually asked to collect**, for either
encoding. The grand-total formula is published; the collectable is not.

This is the only part of this design that can take money incorrectly, so it is
handled as a gate rather than a hope:

- The encoding lives behind one exported constant, `COD_ENCODING`, with two
  implementations (`partial` and `balance-only`). Switching is a one-line
  change, not a rewrite, because the mapping function is the only thing that
  reads it.
- **No parcel is handed to a courier until a label generated by this system
  has been read and the collectable amount on it confirmed as ₹4,500.** Label
  generation dispatches nothing, so this is free to do.
- If the label reads ₹4,999, the constant flips to `balance-only` and the
  label is checked again.

## Prerequisites outside the code

None of these are things this repository can do, and all of them block a real
shipment. They belong in the plan as a checklist, not as tasks.

- A Shiprocket account with a **dedicated API user** (Settings → API). The
  panel login does not authenticate against `/auth/login`.
- **KYC and bank verification complete.** COD parcels can be shipped before
  this; the money is not remitted until it clears. Shipping first means cash
  accumulating at Shiprocket with no way to draw it.
- A **registered pickup address**, by nickname. `pickup_location` cannot name
  a new address; an unknown name is refused.
- A **funded wallet**. AWB assignment fails below a minimum balance.
- A webhook URL and token configured in the dashboard. There is no API for
  this.

## Architecture

### The client

`lib/shiprocket/client.ts` — a thin typed client over
`https://apiv2.shiprocket.in/v1/external`. Six endpoints, no SDK: there is no
official Node SDK, and a third-party wrapper would lag Shiprocket's monthly
additive releases. Types are generated from the published OpenAPI document so
field names stay honest.

Authentication is a JWT valid for ten days with **no refresh endpoint**. The
token is cached in Postgres, not in module scope — serverless instances do not
share memory, and a per-invocation login would hit the lockout:

> *"Too many failed login attempts. Please try after half an hour."*

The client re-logs in only on a 401. Login failures are not retried in a loop.

**Every response is checked in its body, never by status code alone.**
`assign/awb`, `generate/pickup`, `generate/label`, `manifests/generate` and
`courier/serviceability` all return business failures inside HTTP 200 — an
empty wallet arrives as `200 {"awb_assign_status": 0, "status_code": 350}`.
The client exposes a single `ok` discriminant computed from the documented
in-body flag for each endpoint, so callers cannot accidentally branch on
`res.ok`.

Requests send `verbose: true`, which turns business-rule failures into a
structured 422 with a field map instead of an unparseable string.

### The mapping

`lib/shiprocket/map.ts` — a pure function from a `preorder` row to the create
payload. No I/O, so it is tested exhaustively. This is where every sharp edge
in Shiprocket's validation lives:

| Rule | Consequence if unhandled |
|---|---|
| Phone: exactly 10 digits, India | `+91 98765 43210` is rejected |
| Phone made of one repeated digit is rejected | `9999999999` fails validation |
| `billing_pincode`: 6 digits, ≥ 100000 | a leading-zero pincode fails |
| `billing_city`: max 30 chars | silently rejected, not truncated |
| `billing_address`: 3–190 chars including line 2 | rejected |
| `billing_last_name`: required key, value may be empty | a one-word name 400s |
| `order_id`: ≤50 chars, no `? ! = + \ , * ^ %` | rejected |
| `order_date`: not more than 6 months old | an old preorder is rejected |
| Duplicate SKU within one order | rejected |

The preorder table holds a single `name` and a single `address`; Shiprocket
wants first and last name separately and enforces a length ceiling. The
mapping splits on the last space and sends an empty last name when there is
no space. Addresses longer than 190 characters are a mapping **error**, not a
truncation — silently cutting an address produces an undeliverable parcel.

`order_id` is the preorder's primary key, prefixed. Shiprocket's create is
**idempotent on `(order_id, channel_id)`**: re-posting a known `order_id`
returns the existing order unchanged. That makes the primary key a natural
retry key, and it is never reused — a cancelled order burns its id forever.

### The dispatch chain

`lib/shiprocket/ship.ts` — four calls, each persisted before the next begins,
so a failure resumes rather than restarts:

```
serviceability (cod=1, declared_value)   → is this pincode COD-serviceable at all
  → create order                         → sr_order_id, sr_shipment_id
    → assign AWB                         → awb_code, courier_name
      → generate pickup                  → pickup_scheduled_date, pickup_token
        → generate label                 → label_url
```

Nothing in this chain is idempotent except the create, so the gate is ours:
each step checks the column the previous step wrote and refuses to run twice.
AWB assignment is capped by Shiprocket at three per shipment per day and
pickup returns `400 "Already in Pickup Queue."` — those are backstops, not the
design.

Serviceability failure arrives as `{"status": 404}` inside a 200 and must be
surfaced to the admin before an order is created, not after.

**`generate/pickup` is the call that summons a courier.** It is the boundary
between reversible and not, and it is the only step the admin confirms
separately.

### Status in

`app/api/webhooks/logistics-ingest/route.ts`. The path deliberately contains
none of `shiprocket`, `kartrocket`, `sr`, `kr` — Shiprocket's documentation
requires their absence from the URL.

Authentication is a shared secret echoed back in an `x-api-key` header,
compared in constant time. That is the only mechanism Shiprocket offers: no
signature, no body signing, no documented IP allowlist, and the token is
*optional* in their dashboard, meaning an unconfigured endpoint is open to
anyone who guesses the URL.

**Therefore the webhook is a hint, not an authority.** It writes to
`shipment_events` and updates display status. Before any financial column is
written, the server re-reads `GET /orders/show/{id}`. A forged "delivered" can
move a progress bar; it cannot move money.

Matching: the webhook's `order_id` is a composite string
(`"<channel_id>_<something>"`) and is neither our id nor the Shiprocket order
id. Rows are matched on `awb` or `sr_order_id` only.

`scans[]` is the full history on every delivery, not a delta, so events are
upserted on `(awb, scanned_at, status)` and repeated deliveries are free.
`current_status_id` and `shipment_status_id` are different numbers for the
same label — two separate code spaces — so **logic keys off the uppercase
status string**, never the numeric code. Shiprocket publishes no complete code
table; the numbers are recorded for later study and nothing branches on them.

### Money in

This is the part worth being pedantic about.

`delivered` means a courier says they handed a box over. It does not mean the
company has ₹4,500. Shiprocket remits COD on roughly **D+8 working days**,
paid out Monday, Wednesday and Friday, and only once KYC has cleared.

So `preorders.balance_collected_at` is written **only** when
`GET /orders/show/{id}` returns a non-null `remittance_utr`, and the UTR is
stored beside it. Delivery sets `fulfilment = 'delivered'` and nothing else.
There is no API for remittance as such; the fields hang off the order.

A daily cron lists COD orders delivered in the last 30 days and polls
`orders/show` for those whose UTR is still null. `remittance_status`'s
enumerated values are undocumented, so the string is stored verbatim and
nothing branches on it.

### Schema

New columns on `preorders`, all nullable — an order that has never shipped
has none of them:

```
sr_order_id             bigint      -- Shiprocket's order id
sr_shipment_id          bigint
awb_code                text
courier_name            text
sr_status               text        -- last known status string, uppercase
sr_status_at            timestamptz
pickup_scheduled_date   date
label_url               text
remittance_utr          text        -- bank UTR of the COD payout
remittance_status       text
remittance_date         date
cod_amount_paise        integer     -- what we asked the courier to collect
```

`cod_amount_paise` records what was *actually sent* rather than recomputing
it, so a later change to the encoding cannot rewrite history.

One new table:

```
shipment_events (awb text, scanned_at timestamptz, status text,
                 activity text, location text, raw jsonb,
                 primary key (awb, scanned_at, status))
```

The natural primary key is what makes redelivered webhooks idempotent.

### Admin

The Ship action lands on the orders page from `feat/insights-dashboard`,
reusing its `fulfilment` vocabulary: `new → packed → shipped → delivered`.
Shiprocket drives transitions from `packed` onward; a human still marks a unit
`packed` when it is built, because nothing else knows that.

Each row shows AWB, courier, last status and — once it exists — the
remittance UTR. Where a step failed, the row shows which step and offers a
retry of that step alone.

## Privacy

Shipping sends name, phone, full address and email to Bigfoot Retail Solutions
(Shiprocket) and onward to whichever courier carries the parcel. The published
`/privacy` page currently names Mixpanel and "the courier" only. It must name
Shiprocket, state what is sent and why, before the first parcel ships. This is
a release gate, not a nicety.

Nothing about a buyer goes to a language model. The existing rule stands.

## Failure handling

Every step records its own failure against the order, so the admin can see
which one failed rather than a generic error:

- **Pincode not COD-serviceable** — surfaced before order creation. The order
  cannot ship; it needs a conversation with the buyer.
- **Wallet empty** — `status_code: 350` inside a 200. Surfaced as "recharge
  the Shiprocket wallet", not as a server error.
- **Validation rejected** — the 422 field map is shown against the field, so a
  bad phone number is fixable in the admin rather than in the database.
- **Token expired** — one re-login, then the original call retried once.
- **Rate limited** — 429 with `Retry-After`; the admin is told to wait rather
  than the call being retried in a loop.

## Testing

**There is no Shiprocket sandbox.** The OpenAPI document declares exactly one
server, production, and their usage guidelines state that any request with
valid credentials affects real data. Testing is therefore layered:

- `map.ts` is pure and gets exhaustive unit tests against every validation
  rule in the table above. This is where most of the risk lives and it costs
  nothing to cover.
- The client's response handling is tested against recorded fixtures,
  including the 200-with-failure shapes, since those are the trap.
- The webhook route is tested for a wrong token, a missing token, a replayed
  delivery, and an unknown AWB.
- Against the real API, only the read-only and reversible calls run:
  serviceability, create, label. `generate/pickup` is never called by a test.
- An order created in testing is cancelled through `POST /orders/cancel`.
